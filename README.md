# AKS Quota Auto-Approval

This project demonstrates an AI-assisted, policy-driven Kubernetes quota approval workflow for AKS. The system validates quota requests, evaluates cluster usage, and applies deterministic infrastructure policies before a request is approved or escalated.

## Features

- FastAPI API for quota submission and lookup
- Deterministic infrastructure policy evaluation
- Agent-based reasoning with CrewAI-style orchestration patterns
- Azure helper layer with managed identity-friendly abstractions
- Teams notifications for audit visibility
- Docker and Kubernetes deployment manifests

## Quick start

1. Create a virtual environment and install dependencies:
   ```bash
   python -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```
2. Copy the example environment file and update the values:
   ```bash
   cp .env.example .env
   ```
3. Run the application:
   ```bash
   uvicorn app.main:app --reload
   ```
4. Submit a request:
   ```bash
   curl -X POST http://localhost:8000/quota/request \
     -H 'Content-Type: application/json' \
     -d '{
       "application_name": "payment-service",
       "namespace": "payments",
       "requested_cpu": "4",
       "requested_memory": "16Gi",
       "environment": "production",
       "requester": "user@example.com",
       "business_justification": "Required for production workload"
     }'
   ```

## Architecture Overview

This solution implements an AI-assisted quota approval platform for Azure Kubernetes Service (AKS). The platform accepts a resource request for CPU and memory, evaluates the current AKS cluster health and capacity, applies a deterministic infrastructure policy, and decides whether to approve, scale, reject, or require human approval.

The design intentionally separates:

- AI reasoning and analysis from
- the actual infrastructure control plane and governance rules.

In practice, CrewAI can inspect cluster telemetry and explain context, but the final authorization decision is enforced by deterministic Python logic.

## High-Level Architecture

```text
User / Application
        |
        v
FastAPI API
        |
        v
Quota Request Validation
        |
        +--> CrewAI analysis (AKS, Azure Monitor, capacity, policy)
        |
        +--> Deterministic Policy Engine
                    |

                    +--> HUMAN_APPROVAL_REQUIRED

                    |
                    v

```

## Workflow

1. A user submits a quota request through the FastAPI endpoint.
2. The request is validated using Pydantic models.
3. A request ID is generated and the request is stored for lookup.
4. AKS and Azure Monitor data are gathered through explicit, validated tool functions.
5. CrewAI agents analyze the infrastructure signals, node pool status, and cluster capacity.
6. A deterministic policy engine evaluates:
   - CPU and memory utilization thresholds
   - allocatable capacity
   - request fit
   - node pool maximum bounds
   - scaling feasibility
7. The system decides one of the following:
   - APPROVED
   - SCALED_AND_APPROVED
   - REJECTED
   - PENDING_HUMAN_APPROVAL
8. A Microsoft Teams notification is sent for every decision.
9. The final request record can be retrieved with the request lookup API.

## Component Responsibilities

### 1. FastAPI Layer
The API layer exposes:

- POST /quota/request
- GET /quota/request/{request_id}
- GET /health

It validates request payloads, initiates decision processing, and returns a consistent response contract.

### 2. Request & Decision Models
The platform uses Pydantic models for:

- quota requests
- policy outputs
- decision records

This ensures the API contract is explicit and strongly typed.

### 3. Policy Engine
The deterministic policy engine is the final decision authority. It checks:

- CPU usage threshold
- memory usage threshold
- allocatable capacity versus requested resources
- node pool limit enforcement
- max capacity and scale constraints

The policy is intentionally not delegated to the LLM.

### 4. CrewAI Agents
The AI layer is organized into specialized roles:

- infrastructure analyst
- capacity planner
- policy validator
- approval decision orchestrator

The agents use tool-backed execution when an LLM is configured; otherwise they execute the same deterministic tool flow without requiring a live model.

### 5. Azure Integration Layer
The Azure integration layer encapsulates the cloud control plane access. It includes:

- Azure authentication via DefaultAzureCredential or ManagedIdentityCredential
- AKS cluster metadata retrieval
- Azure Monitor metrics retrieval
- node pool scaling logic
- validation of configuration and quota prerequisites

### 6. Notification Service
Teams notifications are generated as MessageCard payloads for each outcome:

- approval
- scale + approval
- rejection
- human approval required

This supports operational visibility and auditability.

- AZURE_USE_MANAGED_IDENTITY: used when running in Azure-hosted environments with managed identity

## Decision Logic

The decision engine applies deterministic checks before approving any request.

### Approval Condition
The request is approved when:

- CPU utilization is below threshold
- memory utilization is below threshold
- request fits within allocatable capacity
- no conflicting policy violation exists

### Scale Condition
If the cluster is near or above threshold, the system evaluates whether scaling is possible:

- node pool can add nodes
- node pool max limit is not exceeded
- required infrastructure validation passes
- the request remains safe after scale

### Reject Condition
The request is rejected when:

- the node pool is at maximum capacity
- the cluster cannot support the request safely
- policy constraints are violated

### Human Approval Condition
The system enters human approval when:

- monitoring data is unavailable
- Azure validation cannot be confirmed
- resource data is inconsistent
- confidence is insufficient
- policy and capacity results disagree

## Safety and Security Model

The solution is designed with production safety in mind.

- no arbitrary Azure CLI commands are generated by the LLM
- cloud actions are performed via explicit Python functions
- all parameters are validated before execution
- no secrets are embedded in code
- Azure authentication uses managed identity or default credential chain
- webhook usage is externalized through environment configuration
- every action is auditable and traceable
- the deterministic policy layer is the final source of truth

## Operational Considerations

### Stability
- Validate all Azure and Kubernetes input before making changes.
- Keep scaling bounded by configured maxima.
- Fail closed when infrastructure data is unavailable.

### Scalability
- The platform can be expanded with additional cloud providers, namespaces, and policy modules.
- The architecture keeps the policy layer decoupled from AI logic to simplify future extension.

### Maintainability
- Azure and Teams logic are abstracted into tool/service layers.
- Pydantic models enforce clean API contracts.
- Request tracking provides an operational trail for review.

## Summary

This solution demonstrates a realistic self-service infrastructure platform for AKS quota automation. It combines AI-driven analysis with deterministic infrastructure enforcement to improve responsiveness without sacrificing safety, control, or auditability.

The system is intentionally designed so that:

- the LLM assists with understanding and explanation,
- but the code, not the model, makes the trust boundary decision.
